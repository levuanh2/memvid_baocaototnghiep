## Authoritative analysis (from backend node_logs, ground truth)

The JSON `llm_generations=4` UNDERCOUNTS: generations kept running after the
client 420s deadline. Direct `node_logs` query is authoritative:

- Solo baseline (2026-07-06, no load): `GenerateAnswer ok` in **~57s** (56.7s / 58.3s).
- Under 10 concurrent identical (this run): **6 `GenerateAnswer` executions, ALL `error`**,
  durations **248s → 284s each** (~5× the solo time). Every one exceeded
  `AI_TIMEOUT_SEC=180` → RuntimeError "AI timeout" → job error → `ErrorHandler`.

### Verdict
- **0/10 success.** Under 10 concurrent identical questions the system fully
  collapses: unbounded fan-out (~8 admitted = gunicorn 2 × Semaphore(4)) thrashes
  the single CPU Ollama; each generation slows ~5× and blows past the 180s timeout.
- **Cache gave zero relief**: no generation ever completed, so nothing was seeded
  (`cache hits = 0`). Cache cannot help a cold stampede — only a completed first
  answer can, which never happened.
- **No single-flight**: 6 distinct generations for the *same* question, all wasted.
  Single-flight would collapse this to 1 generation + 9 waiters.
- **Empty-answer contract HELD**: no `"Không có phản hồi."` returned; failures were
  honest job errors, and errored/empty answers were NOT cached (no poisoning).
- **Admission back-pressure is brutal, not graceful**: 2 queued requests spun on
  HTTP 429 (605 & 676 retries ≈ 5 min each) instead of waiting cleanly.

### Priority confirmed by data
1. **Phase 2 — global LLM cap (`MAX_CONCURRENT_LLM_CALLS≈2`) is THE fix.** At cap 2,
   each gen sees ≤2× contention (~60–90s < 180s) → completes → seeds cache → unblocks
   the rest. Without the cap, nothing finishes.
2. **Phase 3 — single-flight** then collapses identical/paraphrase storms to ~1 gen.
